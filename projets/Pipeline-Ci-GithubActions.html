SECTION A

Création du dépôt GitHub

1 Création du dossier et initialisation de Git

bash
# Créer un dossier pour le projet mkdir Pipeline_CI # Se déplacer dans ce dossier cd Pipeline_CI # Initialiser Git dans ce dossier git init

Explications :
- mkdir Pipeline_CI : crée un dossier pour le projet
- cd Pipeline_CI : entre dans le dossier
- git init : initialise un dépôt Git local

2 Ajouter un fichier README et premier commit

bash
# Créer un fichier README avec un titre echo "# Projet Pipeline CI" >> README.md # Vérifier que le fichier est bien créé dir # (ou ls sur Linux/Mac) # Ajouter le fichier au suivi Git git add README.md
bash
# Créer le premier commit git commit -m "docs: ajout du README initial"

Explications : Le README sert de documentation de base. git add prépare le fichier, git commit l'enregistre dans l'historique.

3 Créer le dépôt distant sur GitHub et lier au local

Via le web :

  • Connectez-vous à GitHub
  • Cliquez sur "New Repository"
  • Repository name : Pipeline_CI
  • Public ou Privé selon besoin
  • Ne pas cocher "Add a README" (déjà créé localement)

En local :

bash
# Lier le dépôt local au dépôt distant git remote add origin https://github.com/<ton-username>/Pipeline_CI.git # Renommer la branche master en main git branch -M main # Pousser le code vers GitHub git push -u origin main

Résolution de conflit possible : si GitHub a un README par défaut, un conflit apparaît.

1. Ouvrir le fichier README.md : marqueurs de conflit :

<<<<<<< HEAD # Projet Pipeline CI ======= # Pipeline_CI >>>>>>> 4d468cb (Initial commit)

2. Choisir le contenu à garder : fusionner ou choisir.

3. Marquer le conflit comme résolu :

git add README.md git rebase --continue

4. Vérifier l'historique :

git log --oneline

5. Pousser vers GitHub :

git push -u origin main

4 Créer et gérer les branches

bash
# Créer une branche develop à partir de main git checkout -b develop # Envoyer la branche develop vers GitHub git push -u origin develop # Créer une branche de fonctionnalité (exemple : tests) git checkout -b feature/tests # Envoyer la branche feature/tests vers GitHub git push -u origin feature/tests

Commentaires :
- git checkout -b develop : crée et bascule sur develop
- feature/tests : branche dédiée aux tests
- git push -u origin : envoie et configure le suivi

5 Protection des branches sur GitHub

Procédure :

  1. Aller dans Settings → Branches
  2. Cliquer sur Add rule

Configurer pour main :

  • Branch name pattern : main
  • Cocher :
    • Require a pull request before merging
    • Require approvals
    • Require status checks to pass before merging

Pour develop : moins strict mais utile :

  • Require a pull request before merging
  • Require status checks to pass before merging
  • Require conversation resolution before merging

Commentaires : La protection des branches empêche les commits directs sur main et force l'utilisation des Pull Requests avec validation CI.

6 Convention de commits et fichier CONTRIBUTING.md

6.1. Convention de commits

Format : <type>(scope): <description>

Types principaux : feat, fix, docs, style, refactor, test, chore

Exemples :

feat(api): ajout d'un endpoint pour les tests fix(ci): correction du script de pipeline docs(readme): mise à jour des instructions d'installation

6.2. Fichier CONTRIBUTING.md

Guide les contributeurs sur la manière de participer.

markdown
# Guide de contribution Merci de contribuer au projet **Pipeline_CI** 🎉 ## Workflow Git - Les contributions se font via des **branches de fonctionnalité** (`feature/...`). - Les branches doivent être fusionnées dans `develop` via **Pull Request**. - La branche `main` est protégée et ne reçoit que du code validé. ## Convention de commits Nous utilisons [Conventional Commits](https://www.conventionalcommits.org/). Format : `<type>(scope): <description>` Types autorisés : feat, fix, docs, style, refactor, test, chore ## Pull Requests - Chaque PR doit être approuvée par au moins un membre. - Les tests et la CI doivent passer avant la fusion. - Les discussions doivent être résolues avant merge.

Application :

bash
git add CONTRIBUTING.md git commit -m "docs: ajout du fichier CONTRIBUTING.md" git push origin develop

Vérification :

git branch # * feature/tests git push origin feature/tests

7 Étapes pour fusionner via GitHub (Pull Request)

7.1 Créer la Pull Request

  • Sur GitHub, cliquer sur "Create pull request"
  • Titre : docs: ajout de CONTRIBUTING.md et mise à jour du README
  • Ajouter une description si besoin

7.2 Valider la Pull Request

  • Approuver la PR (si règle d'approbation)
  • Vérifier que les checks CI passent

7.3 Fusionner

  • Cliquer sur "Merge pull request"
  • Choisir "Create a merge commit" ou "Squash and merge"
  • Confirmer avec "Confirm merge"

Avant de configurer le pipeline CI, ajouter une application Python simple (calculatrice) et des tests unitaires.

8 Workflow Git

bash
git add calculatrice.py test_calculatrice.py git commit -m "feat(calculatrice): ajout de l'application et des tests unitaires" git push origin develop
SECTION B

Responsable du pipeline CI

1 Introduction

Le responsable du pipeline CI est chargé de mettre en place une intégration continue (CI) permettant d'automatiser les tests et de garantir la qualité du code. Cette automatisation permet de détecter rapidement les erreurs, de maintenir un code propre et de faciliter le travail en équipe.

2 Création locale du fichier YAML

Création du dossier caché :

mkdir -p .github/workflows

Fichier .github/workflows/ci.yml :

yaml
name: CI Pipeline on: push: branches: [ main, develop ] pull_request: branches: [ main, develop ] jobs: build-and-test: runs-on: ubuntu-latest steps: - name: Checkout repository uses: actions/checkout@v3 - name: Set up Python uses: actions/setup-python@v4 with: python-version: '3.12' - name: Install dependencies run: | python -m pip install --upgrade pip pip install pytest flake8 - name: Lint with flake8 run: | flake8 . --count --select=E9,F63,F7,F82 --show-source --statistics flake8 . --count --exit-zero --max-complexity=10 --max-line-length=127 --statistics - name: Run tests run: | pytest

Explications :
- Installation des dépendances : pytest, flake8
- Build : préparation Python 3.12
- Tests : exécution pytest
- Linting : vérification style avec flake8

3 Commandes Git utilisées

bash
git branch # Vérifier la branche active git checkout feature/tests # Revenir sur la branche git status # Vérifier l'état git add .github/workflows/ci.yml git commit -m "ci: ajout du pipeline GitHub Actions" git push origin feature/tests

4 Pull Request vers develop

Une fois le fichier ci.yml poussé sur feature/tests, créer une PR vers develop pour revue.

5 Déclenchement automatique du pipeline

Le pipeline se déclenche à chaque push ou PR sur main/develop. Dans l'onglet Actions :

  • Vert = succès
  • Rouge = échec

6 Étapes pour générer un pipeline rouge

6.1 Modifier test_calculatrice.py :

def test_fail(): assert 2 + 2 == 5

6.2 Commit et push :

git add test_calculatrice.py git commit -m "test: ajout d'un test volontairement erroné pour démonstration CI" git push origin feature/tests

6.3 Créer ou mettre à jour la PR vers develop :

Le pipeline CI détecte automatiquement les erreurs et bloque la fusion tant que le code n'est pas corrigé.

7 Correction de l'erreur

7.1 Corriger le test :

def test_fail(): assert 2 + 2 == 4 # ou supprimer le test

7.2 Commit et push la correction :

git add test_calculatrice.py git commit -m "fix(tests): suppression du test erroné pour valider le pipeline CI" git push origin feature/tests

7.3 GitHub relance le pipeline :

Le problème est résolu, le pipeline passe au vert.

SECTION C

Responsable des tests

1 Introduction

Le responsable des tests joue un rôle essentiel dans le projet. Il est chargé de garantir la qualité du code en écrivant et en validant des tests unitaires. Ces tests permettent de vérifier que chaque fonction du programme se comporte comme prévu, et de détecter rapidement les erreurs lors des modifications du code.

2 Mise en place des tests

  • Création du fichier test_calculatrice.py
  • Ajout de tests unitaires pour chaque fonction : addition, soustraction, multiplication, division, puissance, modulo

3 Commandes Git utilisées

bash
git branch git checkout feature/tests git status git add test_calculatrice.py git commit -m "test(calculatrice): ajout des tests unitaires" git push origin feature/tests

4 Déclenchement du pipeline CI

Le pipeline CI exécute automatiquement les tests unitaires à chaque push ou pull request sur main ou develop.

Exemples :

  • Pipeline vert : tous les tests passent
  • Pipeline rouge : un test échoue (comme démonstration avec assert 2+2 == 5)

5 Résultat attendu

  • Pipeline vert : tous les tests passent et le code est validé
  • Pipeline rouge : une erreur est détectée et la fusion est bloquée

6 Conclusion

Le responsable des tests assure la fiabilité du projet en validant le bon fonctionnement du code. Les tests unitaires intégrés au pipeline CI garantissent que chaque modification est contrôlée avant d'être fusionnée. Cela permet de maintenir un haut niveau de qualité et de stabilité dans le projet.
